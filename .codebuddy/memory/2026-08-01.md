## OneNET HEAD 406 联网查证结论

- 背景：ota_transport.c:109-112 注释记录 OneNET Fuse OTA 拒绝 HEAD（406），故 OneNET 路径 `partial_http_download=false` 走完整 GET。
- 联网查证：OneNET 官方 OTA 文档（ota.heclouds.com，旧版 OTA 1.0）所有接口只用 GET/POST，固件下载明确 `GET /ota/south/download/{token}` + Range 头分片（示例 Range:50500-50999），全文无任何 HEAD 方法；GitHub bigmonkeyyo/ESP32_S3_TEST_AI 的 fuse-ota 开发经验（版本上报 POST、check GET、download GET）同样只用 GET/POST，实机闭环 1.3.0→1.3.1 成功。
- 结论：OneNET fuse-ota 下载接口设计上就没有 HEAD 语义，签名鉴权（Authorization version=2022-05-01）与 token 都围绕 GET 设计；406 是网关对不支持方法的状态码映射。支持 Range（官方文档也直接示例 Range 分片），所以"完整 GET + 断点续传"是正确路径，不是降级。

## 语音对话音频缓存机制（official_chat/audio/audio_service，用户问"语音对话如何实现音频缓存"）

- 架构：4 个 std::deque + audio_queue_mutex_ + audio_queue_cv_（condition_variable）组成的生产-消费流水线，背压式有界缓存，无大块缓冲。
- 上行：audio_input_task(读I2S 60ms PCM→重采样16k) → audio_encode_queue_(上限 kMaxEncodeTasksInQueue=2) → AudioTaskWorker(esp_opus_enc 60ms/帧) → audio_send_queue_(上限 kMaxSendPacketsInQueue=40≈2.4s) → WebSocket线程 PopPacketFromSendQueue→SendAudio。背压：send_queue满→停编码→input阻塞→丢实时数据，内存不无限积压。
- 下行：PushPacketToDecodeQueue(wait=true阻塞/false drop计数) → audio_decode_queue_(kMaxDecodePacketsInQueue=40≈2.4s 网络抖动缓冲) → worker(esp_opus_dec) → audio_playback_queue_(kMaxPlaybackTasksInQueue=2) → AudioOutputTask codec_->Write→I2S DMA。
- 常量：kOpusFrameDurationMs=60, kMaxDecodePacketsInQueue=2400/60=40, kMaxSendPacketsInQueue=40, kMaxTimestampsInQueue=3, kAudioTestingMaxDurationMs=10000。MaybeLogQueueStats 每1s打印队列深度。
- 对比：memory_watch_recorder.c 语音备忘录是流式无缓存（60ms帧 read→重采样Q16线性插值→Opus→Ogg→write_cb，三个 PSRAM 小缓冲）；danger_sample_recorder.c 危险样本是真环形缓冲（3s×16k=48000样本 PSRAM，写指针取模回绕，触发时 copy_range 取前1s+后1s，SD写用 FreeRTOS queue 4槽分离写任务）。\n- 语音备忘录"流式不缓存"的准确含义（用户追问"为什么不缓存"）：PCM 层不缓存，但 service 层 memory_watch_service_audio_write_cb 把 Ogg 逐块 memcpy 进 PSRAM 动态 buffer（8KB 起倍增，上限 MEMORY_WATCH_VOICE_CLIENT_MAX_AUDIO_BYTES=6MB），录完再 send_voice_over_ws 或 post_voice_http 整段上传。原因：①不需要预存触发前音频（用户按下才开始，无需回溯，对比危险样本环形缓冲的理由）；②同步单任务循环（s_upload_worker_queue worker），write_cb 慢即同步阻塞，天然背压，无需队列解耦；③内存经济（60ms帧 PCM≈1.9KB，三个缓冲约5KB，缓存2.4s需~150KB纯浪费）；④60ms 对齐 Opus 帧边界与 official_chat kOpusFrameDurationMs=60 一致。三链路缓冲对照：危险样本=环形缓冲(事后回溯触发前音频)、语音对话=有界队列(异步网络抖动缓冲+背压)、语音备忘录=流式帧(按下才开始+同步单任务+录完才传)。
- 为什么流式60ms帧不丢数据（用户追问）：audio_codec_read 是"凑满才返回"的阻塞读（audio_codec.c read_with_timeout_slice，while transferred<bytes 循环拼凑直到满，超时才 break）；recorder 校验 bytes_read==hw_bytes 否则 cleanup。数据连续生产（I2S DMA 环形缓冲攒着没取走的数据），60ms 只是消费粒度；消费慢→DMA积压不丢(除非溢出)，消费快→read 阻塞等下一批。丢数据仅两种：DMA溢出（编码几ms/60ms，远快于实时，不会溢出）或超时（无数据=无声音可录，主动放弃）。60ms=消费方式而非生产方式。
- DMA 环形缓冲为什么"满的时候也不丢"（用户追问并发机制，关键认知纠偏）：不是"装满60ms水桶才通知"，是"每填满一个描述符(10ms)就中断入队"的流水线。证据：IDF v5.5.3 esp_driver_i2s/i2s_common.c 的 i2s_dma_rx_callback 每填满一格就 xQueueSendFromISR(msg_queue, finish_desc->buf)；软件 i2s_channel_read 阻塞 xQueueReceive(msg_queue)，逐格取走。msg_queue 容量 desc_num-1=5（留一格给正在写的 DMA）。DMA 填满一格10ms vs 软件取走几ms，搬得比填得快→队列永远 0~1 格待取，环水位到不了满。环被"填满"的瞬间=read 返回的瞬间，交付完立即清空重填。唯一会丢：软件处理卡死→队列堆满5格→DMA回绕覆盖旧数据→驱动 xQueueIsQueueFullFromISR 时弹掉最旧一格（丢旧保新兜底）。比喻：流水线传送带（每格10ms按铃即取）而非水桶。硬件参数：AUDIO_PLATFORM_HW_SAMPLE_RATE=24000、IN_CH=2、16bit，60ms@24k×2ch×2B=5760B=6描述符。
- 教学补充（用户追问"read消费慢会怎样"，已讲透消费/生产速率边界）：丢数据临界线=处理耗时 vs 环深60ms。处理耗时<60ms→read返回时环已被取空，等待期间DMA从空开始填，永远到不了满→不丢；处理耗时>60ms→DMA在等待期间填满环并回绕覆盖最旧数据，丢量≈处理耗时−60ms。read内部逐格取是微秒级不可能慢，慢只发生在read之外（编码/上传/被高优抢占）。本项目编码几ms vs 60ms余量20倍，丢不了；风险场景=SD写满/网络阻塞/任务抢占。同时澄清"read慢"分粒度慢（要更多数据→延迟大不丢）与速度慢（间隔长→丢）两种。用户已理解"60ms环深=消费粒度=安全边界"同一个数字的自洽性。
- 教学补充2（用户追问"处理耗时>60ms怎么处理"，已给全套解法）：核心思路=问题不在处理慢，在read主循环被拖住；解法是让主循环只做"取走+移交"，慢活挪出去。五方案：①慢活异步化（read取→有界队列→worker处理，项目范例=official_chat背压队列、danger_sample_recorder SD写分离queue）正解；②增大环深（60→120/240ms）治标，只能吸收偶发慢；③read任务提优先级防被抢占假性慢；④处理预算+超时丢帧保流水线（宁丢一帧不死等）；⑤监控队列水位告警降级（项目MaybeLogQueueStats已做）。决策：偶发慢(IO)→异步队列+缓冲，持续慢(CPU)→异步化+worker+优化算法，抢占→提优先级。未来危险检测推理变重时正解=挪独立任务+queue解耦，而非加环深。
- 教学补充3（用户要求"具体底层讲解"两套慢IO分离机制，已读 audio_service.cc/.h 与 danger_sample_recorder.c 全文）：
  - official_chat 背压队列真身=std::deque+std::mutex+std::condition_variable（audio_service.h:171-178 一个锁一个cv保护5个deque），4任务（oa_input 优先级8/6KB 读I2S、oa_opus 优先级2/24KB PSRAM 编解码、oa_output 优先级4/4KB 播放）。两道闸门：encode_queue上限2（PushTaskToEncodeQueue 阻塞式wait，audio_service.cc:879-882）+ opus任务取货条件 send_queue<40（cc:718-725）。完整背压链：WS发送慢→send_queue满40(2.4s缓冲耗尽)→opus停编码→encode_queue满2→input任务阻塞→不再读DMA→DMA环溢出丢音频（兜底）。2 vs 40 差20倍原因：encode里是未压缩PCM(60ms=1920B)闸门收紧；send里是压缩Opus包+网络抖动缓冲(40包扛2.4s)。下行方向策略相反：PushPacketToDecodeQueue wait=true阻塞(PlaySound保证提示音不丢)/wait=false直接丢新包(decode_queue_drop_count)，播放链不能堵。WS线程用PopPacketFromSendQueue取包+on_send_queue_available回调通知。
  - danger_sample_recorder 队列真身=FreeRTOS xQueueCreate(4, sizeof(write_request_t))，队列传"PCM指针+元数据"数据移动不拷贝（write_request_t.pcm_data由写入任务释放）；生产端推理任务只做 malloc+memcpy+xQueueSend(超时0)，满队列→丢弃本次+立即heap_caps_free防泄漏（queue_completed_capture:291-305），微秒级不卡推理；消费端write_task优先级3/栈8KB，xQueueReceive(portMAX_DELAY)零CPU睡觉，建目录+写WAV(.tmp→rename原子)+写JSON+free；失效保护=哨兵(pcm_data==NULL退出信号)+generation(递增使队列残留旧请求作废，stop后不落盘)。
  - 两机制对比：满队策略相反——official_chat 阻塞背压传回采集源头（语音是当下要用的，丢了=AI听错）；danger_recorder 丢新保实时（样本是事后取证，丢了不影响实时推理链）。结论：背压策略由业务语义决定。
