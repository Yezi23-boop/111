## CDN 接入评估：cf 隧道 vs cdnfly CDN（用户咨询"用 CDN 是否不需要 cf"）

- 结论：不是替代关系，是分工。cf 继续管动态 API + Hermes WSS 对话主通道（`wss://watch.934000.xyz/v1/watch/ws`，BuildWsUrl 在 memory_watch_ws_client.cc 把 https 换 wss）；CDN 只接管 OTA 固件 .bin 大文件下载（11MB，30GB/月流量大头）。
- 原因：cf 隧道=内网穿透+实时双向长连接+源站零暴露（不开入站端口）；cdnfly=缓存型 CDN，只能缓存静态文件让用户取货，要求源站开放公网端口给 CDN 回源，对 WebSocket 长连接支持差。两种产品哲学对立。
- 推荐落地：DNS 分流。`ota.934000.xyz` 走 CDN（IP 源站=阿里云、强制 Range、.bin 缓存 7-30 天、忽略查询参数）；`watch.934000.xyz` 保持 CF Tunnel。服务器 manifest 返回固件 URL 指向 ota 域名。
- **代码改动点（关键发现）**：`ota_transport.c:159` `ota_transport_host_matches` 是单 host 严格匹配（strlen+strncmp），manifest URL 和 image URL 共用 `CONFIG_OTA_SERVICE_REMOTE_ALLOWED_HOST`（Kconfig.projbuild:80，默认 watch.934000.xyz）。固件换到 ota 域名必须改：省事版=allowed_host 改 ota 域名+manifest 也跟着走 CDN（0 缓存透传多一跳）；干净版=Kconfig 拆 MANIFEST_HOST + IMAGE_HOST 两个值，host_matches 分别校验（约 15 行）。
- "末尾断流"问题代码层已解决（ota_transport.c:35-40 Range 分块 256KB kOtaPartialRequestBytes + 60s 无进度超时），CDN 的 Range 是锦上添花非雪中送炭。
- 用户理解进展：需用大白话解释"CDN 是仓库只负责取货、cf 隧道是实时电话"。用户尚未决定是否落地 host 拆分改动。
- **最终方向修正（用户自己意识到）**：用户只有 1 台设备，CDN 缓存红利（多人摊一次回源成本）= 0，cdnfly 方案**不落地**。优化建议改为：cf 隧道直接下载 OTA 固件已够用；如想再优化，用 Cloudflare 免费版 Cache Rule 缓存 .bin（上限 100MB，11MB 固件够），零成本不暴露 IP。代码层 host 拆分改动（MANIFEST_HOST + IMAGE_HOST）不再需要，除非以后多设备大批量部署。
