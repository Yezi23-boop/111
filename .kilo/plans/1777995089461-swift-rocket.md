# LVGL 中文字库生成与 LittleFS 文件系统加载方案

## 背景

当前项目 `assets` 分区（2MB）使用 `partitions.csv` 中的 `spiffs` subtype 标记，但代码中 `ui_font_assets.c` **并未使用 SPIFFS API**，而是通过 `esp_partition_mmap()` 直接 mmap 读取 raw 二进制数据，再用 `cbin_font_bridge_create()` 解析自定义 cbin 格式字体。

目标：用 LVGL 原生方案替代整个自定义 cbin 链路。

## 最终需求

1. **字体来源**：`montserratMedium.ttf`（拉丁字符）+ `LXGWWenKai-Regular.ttf`（中文字形）
2. **字符集**：《通用规范汉字表》(8105字) + ASCII 基本字符 (0x20–0x7E)
3. **生成工具**：`lv_font_conv` 1.5.3（`npx lv_font_conv`）
4. **输出格式**：`.bin`（LVGL 原生二进制格式）
5. **文件系统**：`assets` 分区从当前"raw mmap"迁移到 **LittleFS**
6. **加载方式**：LVGL 原生 `lv_binfont_create("A:xxx.bin")`，启用 `LV_USE_FS_LITTLEFS`
7. **当前阶段**：先生成 `.bin` 文件，暂不改动硬件项目代码

## 与 xiaozhi-esp32 的区别

| | xiaozhi-esp32 | 本项目 |
|---|---|---|
| 字体格式 | 自定义 cbin 格式 | LVGL 原生 `.bin` 格式 |
| 生成工具 | 预编译，checked-in | `lv_font_conv` |
| 加载方式 | `cbin_font_create()` 内存解析 | `lv_binfont_create()` 文件系统加载 |
| 文件系统 | 不使用（raw mmap） | LittleFS |

## 实施步骤

### 第 1 步：生成《通用规范汉字表》字符列表（当前阶段）

创建 `scripts/build_lxgw_font.py`，功能：
1. 用 `fonttools` 打开 `LXGWWenKai-Regular.ttf`，提取所有可用 CJK 字符的 Unicode 码点
2. 对照《通用规范汉字表》范围筛选（主要是 CJK 基本区 U+4E00–U+9FFF 的 8105 字）
3. 输出 `scripts/lxgw_charset.txt`，格式：每行一个十六进制 Unicode 码点
4. 同时输出 `montserratMedium.ttf` 的 ASCII 范围 (0x20–0x7E)

### 第 2 步：用 `lv_font_conv` 生成 `.bin`（当前阶段）

```bash
npx lv_font_conv \
  --font D:\esp32S3\字体\montserratMedium.ttf -r 0x20-0x7E \
  --font D:\esp32S3\lxgw-wenkai-v1.522\LXGWWenKai-Regular.ttf -r 0x4E00-0x9FFF \
  --size 22 --bpp 4 --format bin \
  -o D:\esp32S3\111\build\lxgw_wenkai_22.bin
```

预估文件大小：22px + 4bpp + ~8100 CJK + ASCII ≈ 2-4MB

### 第 3 步：LittleFS 迁移（后续阶段，需要硬件验证）

#### 3a. 分区表修改

当前分区表（已更新）：
```
factory,  app,  factory, 0x10000, 10M,
assets,   data,   spiffs,  ,      2M,
model,    data,   spiffs,  ,      4M,
audio,    data,   spiffs,  ,      6M,
```

迁移 LittleFS 时，`assets` 分区 subtype 改为：
```
assets,   data, littlefs,  ,  2M,
```

#### 3b. ESP-IDF 配置

`idf_component.yml` 添加依赖：
```yaml
dependencies:
  espressif/esp_littlefs: "*"
```

`sdkconfig` 添加：
```
CONFIG_LV_USE_FS_LITTLEFS=y
CONFIG_LV_FS_LITTLEFS_LETTER=65     # 'A'
CONFIG_LV_FS_LITTLEFS_PATH="/assets"
CONFIG_LV_FS_LITTLEFS_CACHE_SIZE=0
```

#### 3c. 构建脚本改造

`CMakeLists.txt` 将 `esptool_py_flash_to_partition` 改为 `littlefs_create_partition_image`：
```cmake
littlefs_create_partition_image(assets ${CMAKE_SOURCE_DIR}/assets/flash FLASH_IN_PROJECT)
```

#### 3d. `ui_font_assets.c` 重写

废弃 `esp_partition_mmap` + `cbin_font_bridge_create` 方案，改用：
```c
lv_font_t *font = lv_binfont_create("A:lxgw_wenkai_22.bin");
```

#### 3e. 移除旧依赖

- `components/78__xiaozhi_fonts` 中的 `cbin_font.c` / `cbin_font_bridge.c` 可移除
- `assets/ai-fonts/font_puhui_common_20_4.bin` 替换为新生成的字体

### 第 4 步：字体加载代码（后续阶段）

改写 `ui_font_assets.c`：
- `ui_font_assets_init()` 中调用 `lv_binfont_create("A:lxgw_wenkai_22.bin")`
- `ui_font_assets_title/body/meta()` 返回加载的字体
- 加载失败时回退到编译字体 `lv_font_SourceHanSerifSC_Regular_22`

### 第 5 步：测试验证（后续阶段）

- LittleFS 分区挂载成功
- `lv_binfont_create()` 加载 `.bin` 字体成功
- UI 显示中文文字渲染正确
- 对比 LXGWWenKai 与 SourceHanSerifSC 渲染效果

## 风险与注意事项

1. **2MB 分区限制**：LittleFS 有元数据开销（约 5-10%），2MB 分区实际可用约 1.8-1.9MB。如果 `.bin` 超过此大小，需要扩大分区或减少字符集
2. **CJK 基本区全量** (U+4E00–U+9FFF) 包含 20992 码位，但 `lv_font_conv` 只提取字体中存在的字形。LXGWWenKai 覆盖很全，预估 `.bin` 约 3-5MB，可能超出 2MB 分区
3. **应对方案**：如果超限，可缩小字符范围到 GB2312 (6763字) 或分级字表
4. **旧系统兼容**：迁移前需确保 `font_puhui_common_20_4.bin` 不再被其他模块依赖
5. **LittleFS 组件**：需添加 `espressif/esp_littlefs` 依赖，确认与 ESP-IDF v5.x 兼容
