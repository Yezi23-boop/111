## 危险告警通知小程序方案讨论

用户问：手表识别到危险后能否通过 MQTT 通知微信小程序。

关键结论：
- **微信小程序不支持 MQTT**，只支持 HTTPS 和 WebSocket(wss://)，无法直接 subscribe MQTT topic。
- 即便用 MQTT 方案也必须经服务器桥接（服务器 subscribe MQTT → 转 WSS/订阅消息推给小程序），MQTT 这层对"手表→小程序"方向是多余的。
- 推荐方案：复用现有 HTTP 通道。手表 `danger_detection_service` 触发 RISK_ALERTING 时 POST 到服务器 :8787，服务器转发到小程序（WSS 前台实时 + 微信订阅消息后台兜底）。
- MQTT 在本项目的正确方向是 **服务器→手表** 的低功耗唤醒（Hermes 草案第 12 节预留），不是手表→小程序。
- 手表危险检测模块：`main/features/danger_detection/danger_detection_service.{h,c}`，支持 Edge Impulse 3 分类和 ESP-DL 二分类两种后端，识别 horn/siren/danger。

## OneNet 与微信小程序通信能力联网调研

用户要求联网搜索 OneNet 能否与小程序通信。搜索结果确认：

**OneNet 可以与微信小程序通信，但不是 MQTT 直连。** 小程序沙箱禁止原始 TCP 连接，只能用以下两种方式：

1. **HTTP 轮询**：小程序用 `wx.request()` 调 OneNet REST API (`iot-api.heclouds.com`)，GET 设备属性 / POST 下发命令。需带 authorization token（含 product_id/device_name/签名）。常见做法是 `setInterval` 每 3 秒轮询。延迟 3~5s。
2. **WebSocket 推送**：OneNet 支持数据变化时通过 WSS 推送，小程序用 `wx.connectSocket()` 接收。延迟 <1s，但只在小程序前台时有效。
3. **HTTP 回调(webhook)**：OneNet 可配置数据触发 HTTP 回调到自建服务器，再由服务器转发到小程序。

MQTT 只在"设备 → OneNet"这一段使用，"OneNet → 小程序"必须转成 HTTP 或 WebSocket。

参考文章：
- CSDN 2302_80667342: onenet 连接微信小程序（mqtt 协议）
- CSDN weixin_35696112: 微信小程序与 OneNet 双向通信实战：HTTP+WebSocket 双模架构
- 腾讯云开发者: 物联网+mqtt+微信小程序（ESP8266+OneNET+小程序）

对当前项目的结论：手表已有 HTTP 直连自建服务器的通道，加 OneNet 做告警通知 = 手表→OneNet→服务器→小程序，多了一层中转。OneNet 更适合需要设备管理/数据可视化/多设备管理的场景。

## MQTT 低功耗方案讨论（用户明确需要 MQTT 做低功耗）

用户明确表示"我需要 MQTT 做低功耗"。这与 Hermes 架构文档第 12 节预留的 MQTT 低功耗唤醒方向完全一致。

核心痛点：当前手表为了等 Hermes 回复，要么 WSS 常开（Wi-Fi 持续活跃），要么 HTTP 每 5s 轮询（频繁唤醒），功耗高。

MQTT 低功耗方案：
- **路径1（服务器→手表）**：服务器发 OneNet 推送命令 → OneNet MQTT push 到手表 → 手表被唤醒 → HTTP 拉取 conversation/inbox 正文。MQTT keepalive 可拉到 5 分钟，期间 ESP32 可 light sleep。
- **路径2（手表→服务器）**：手表危险检测 RISK_ALERTING → MQTT publish 告警数据（label+confidence+timestamp，<200字节）→ OneNet HTTP webhook 回调服务器 → 服务器转发到小程序。

与现有架构的对接：
- MQTT 只传唤醒信号（几十字节），conversation/inbox 正文仍走 HTTP 拉取 — 与 Hermes 草案第 12 节原则一致。
- 需要新增 ESP32 mqtt_client 组件连接 OneNet broker。
- 需要替换 memory_watch_service 的 WSS 常开/HTTP 轮询逻辑为 MQTT 唤醒 + 按需 HTTP。
- 服务器侧需新增 OneNet API 调用（发推送 + 接收 webhook）。
- 现有 power_policy 已有 STANDBY 状态和 Wi-Fi power_save 机制，MQTT 可对接。

## 危险告警上报（手表→服务器）具体落地方案

用户问"手表→服务器（危险告警上报）怎么做"。给出了 MQTT 方案的完整实现细节：

- **注入点**：`danger_detection_service.c` 的 `danger_detection_on_espdl_result` 回调中 `should_raise_alert=true` 分支（约第424行），加一行 `onenet_mqtt_publish_danger_alert()`，不影响现有本地告警逻辑。
- **新增组件**：`components/onenet_mqtt/`，用 ESP-IDF `esp_mqtt_client` 连 OneNet broker (mqtts.heclouds.com:1883)，topic=`$dp`，payload=OneNet旧版JSON数据点格式(3字节头: 0x01+2字节大端长度+JSON body)。
- **MQTT payload**：~120字节 JSON `{device_id, alert_seq, label, confidence, timestamp}`。
- **OneNet配置**：创建产品+注册设备+配置数据流转webhook→服务器 `POST /v1/watch/danger-alert`。
- **服务器端**：`server/watch_voice_endpoint/app.py` 新增 `POST /v1/watch/danger-alert` 端点，接收OneNet webhook，写入inbox + WSS推送小程序。
- **降级策略**：MQTT断连时降级为HTTP POST直连服务器（复用 memory_watch_voice_client 通道）。
- **关键约束**：OneNet MQTT token需要HMAC-SHA256签名(Base64Decode(access_key)作key)，是唯一复杂点。keepalive=120s配合light sleep。
- **FreeRTOS原语选择**：esp_mqtt_client内部已有事件队列，publish为非阻塞（投递到内部发送队列即返回），不会卡住音频推理回调线程。

## 用户决定：危险告警不经过自己的服务器

用户明确表示"为什么要经过我的服务器，我不想经过"。之前方案中 OneNet webhook → 用户服务器 → 小程序的路径被否决。

**不经服务器的两条路径：**
1. **小程序前台**：OneNet WSS API / EMQX MQTT.js WSS 直连小程序，手表 MQTT publish → broker → 小程序实时收到，零服务器参与。
2. **小程序后台**：OneNet/EMQX webhook → 微信云函数（腾讯托管 Serverless，不是用户的服务器）→ 微信订阅消息 → 手机系统通知。

## EMQX vs OneNet 方案对比（用户问 EMQX）

联网调研 EMQX Cloud 后的关键结论：

**EMQX Cloud Serverless 免费版配额：**
- 最大在线连接数 1000，部署 TPS 上限 1000/s，单个客户端发布 TPS 10/s
- 数据集成规则 4 条、动作 4 个、连接器 2 个
- 可创建最多 2 个 Serverless 部署

**EMQX 对小程序的支持（EMQX 官方文档）：**
- 原生支持 MQTT over WebSocket，小程序用 MQTT.js 库直连
- 连接地址格式：`wxs://${host}:8084/mqtt`（注意是 `wxs://` 不是 `wss://`）
- 小程序引入 `mqtt.min.js`（v4.2.1），`mqtt.connect()` 直连
- 需在微信公众平台配置 socket 合法域名
- 专有版部署需绑定域名 + TLS/SSL 证书；真机调试要求域名 ICP 备案

**EMQX vs OneNet 核心差异：**
| 对比项 | EMQX | OneNet |
|---|---|---|
| 小程序角色 | 完整 MQTT 客户端（pub+sub） | 平台 API 消费者（主要收推送） |
| 双向通信 | 原生支持，小程序可 publish 回手表 | 主要单向推送 |
| MQTT 协议 | 标准 MQTT 5.0 | 专有 $dp 格式（Type+Len+JSON） |
| 设备管理面板 | 基础 | 丰富，带数据可视化 |
| 后台通知 | 规则引擎 → webhook → 微信云函数 | 数据流转 → webhook → 微信云函数 |
| 自托管选项 | 开源可自建 | 仅托管 |

**结论：EMQX 更适合用户的"不经过服务器"需求**——小程序成为完整 MQTT 客户端，手表 publish 告警 topic → EMQX broker 直接路由 → 小程序 subscribe 收到，纯 pub/sub 不需要任何转换层。OneNet 的 $dp 专有格式和平台 API 模式反而增加了复杂度。

## 8084 端口与 ICP 备案问题（用户问"如果不支持8084呢"）

联网查证微信小程序网络文档和 EMQX Cloud Serverless 连接指引后的关键发现：

**8084 端口本身不是问题：**
- 微信小程序 wss 域名不限制端口。微信官方文档原文：「对于 wss 域名，无需配置端口，默认允许请求该域名下所有端口」
- EMQX Cloud Serverless 只支持 TLS 加密连接：MQTT over TLS (8883) 和 WebSocket over TLS (8084)，不支持 1883/8083
- 所以 8084 端口在微信小程序里完全合法可用

**真正的问题是 ICP 备案：**
- 微信要求：socket 合法域名必须经过 ICP 备案
- EMQX Cloud Serverless 给的域名形如 xxx.emqxsl.cn，大概率没有 ICP 备案
- EMQX Serverless 不支持 CNAME 自定义域名 → 没法用自己的备案域名

**三种解法对比：**
| 解法 | ICP备案 | 费用 | 小程序角色 | 用你的服务器 | 端口 |
|---|---|---|---|---|---|
| EMQX 专有版 | 自定义域名OK | 付费 | 完整MQTT客户端 | 否 | 可配443 |
| OneNet | heclouds.com已备案 | 免费 | 平台API消费者 | 否 | 平台端口 |
| 自建EMQX | 自己域名OK | 服务器成本 | 完整MQTT客户端 | 是 | 自己定 |

**最终结论：** 在"不用自己服务器 + 免费 + 能过小程序白名单"三个约束下，OneNet 是唯一可行选择。EMQX Cloud Serverless 因 ICP 备案问题无法加入小程序白名单；EMQX 专有版要付费；自建 EMQX 要用用户的服务器。OneNet 的 heclouds.com 作为中国移动平台域名已备案，免费可用，虽然 $dp 格式和平台 API 模式不如标准 MQTT pub/sub 优雅，但在备案约束下是唯一现实路径。

## 用户域名未备案的实际影响分析

用户确认"我有自己的服务器，但域名没有备案"。关键结论：**域名未备案只卡住一条线——小程序直接连用户服务器（WSS/HTTPS）。其他所有链路都通。**

- 手表 → OneNet：通（设备不受 ICP 限制）
- OneNet → 小程序：通（heclouds.com 已备案，能进白名单）
- 手表 → 用户服务器：通（手表是设备，不走微信域名白名单）
- OneNet → 用户服务器（webhook）：通（OneNet 发 HTTP POST 到 IP/域名，不需备案）
- 用户服务器 → 微信订阅消息 API：通（出站调用，api.weixin.qq.com 是腾讯域名）

危险告警链路不受影响：手表 MQTT publish → OneNet → WSS 直达小程序（前台告警，不经用户服务器）；后台通知由用户服务器出站调微信订阅消息 API 或微信云函数代劳。用户服务器仍在 Hermes 对话、webhook 接收等环节正常使用。

## OneNet 新版接入方式修正（用户分享 CSDN 文章）

用户分享了 CSDN 文章 https://blog.csdn.net/2402_83581955/article/details/142925672 ，揭示了一个关键问题：**我之前给的方案用的是 OneNet 旧版格式，新注册账号已全部是新版本**。

**新版 OneNet 关键变化（2023年底架构升级后）：**
- 数据格式：旧版 `$dp` topic + Type+Len+JSON → 新版 OneJSON 物模型 `$sys/{pid}/{dev}/thing/property/post`
- OneJSON payload：`{"id":"{product_id}","params":{"key1":val1,"key2":val2}}`，key 必须与物模型定义的标识符严格匹配
- 认证：旧版 HMAC-SHA256 → 新版 HMAC-MD5(DeviceSecret, ProductID+DeviceName+Timestamp)，Base64编码
- Broker：旧版 `mqtts.heclouds.com:1883` → 新版 `mqtt.heclouds.com:6002`（非加密）/ `6001`（TLS）
- 物模型：旧版不需要 → 新版必须先在控制台定义属性字段（标识符、类型、范围），未定义字段数据会被丢弃
- 小程序 API：旧版 `api.heclouds.com/devices/{id}/datapoints` → 新版 `iot-api.heclouds.com/thingmodel/query-device-property?product_id={pid}&device_name={dn}`
- 小程序 token：用 OneNet token v2.0 工具生成用户级 token（非设备级），基于用户ID + 用户AccessKey + HMAC-SHA1
- 小程序获取数据方式：HTTP 轮询（`wx.request` + `setInterval` 3秒），request 合法域名配置 `https://iot-api.heclouds.com`
- 免费版限制：10条/分钟上行频率

**对方案的影响：**
1. 之前给的 `components/onenet_mqtt/` 代码需要全部改：topic、payload 格式、token 生成算法、broker 地址
2. OneNet 控制台必须先创建物模型属性（alert_label, alert_confidence, alert_seq, alert_timestamp），手表才能上报
3. 小程序端是 HTTP 3秒轮询，不是 WSS 实时推送；危险告警场景 3s 延迟可接受但非实时
4. 需要在微信公众平台配置 request 合法域名 `https://iot-api.heclouds.com`（已备案）

## 用户拍板最终方案：危险告警推送手机通知栏

用户经过充分讨论后拍板了最终方案，核心链路：

```
ESP32识别危险 → MQTT上报OneNet → OneNet规则引擎HTTP转发 → 用户云服务器 → 调微信订阅消息API → 手机通知栏
```

**方案要点（用户自己总结）：**
- 只做"危险告警推送到手机通知栏"这一件事，不加 EMQX，不折腾小程序直连 MQTT
- 开发阶段不需要域名：OneNet→服务器用公网IP即可，服务器→微信API是出站请求，开发者工具勾选"不校验合法域名"即可调起订阅授权
- 正式上线才需要备案域名（小程序拉数据、提交审核时）
- 微信订阅消息是系统级通知，锁屏/后台都能收到，比小程序直连MQTT（一切后台就断）可靠得多
- 云服务器只需加几十行代码：接收OneNet webhook + 调微信订阅消息接口

**需要修正的一点：** 用户说"手表端代码不用改"，但手表当前没有MQTT客户端，需要：
1. 新建 `components/onenet_mqtt/` 组件（新版格式：mqtt.heclouds.com:6002，OneJSON物模型，$sys topic，HMAC-MD5 token）
2. `danger_detection_service.c` 的 `should_raise_alert` 分支加一行 publish 调用（检测逻辑不变，只加上报）
3. OneNet控制台先定义物模型属性（alert_label, alert_confidence, alert_seq, alert_timestamp）

**落地步骤：**
1. OneNet控制台：创建产品+注册设备+定义物模型属性+配置数据流转规则（HTTP转发到服务器公网IP）
2. 微信公众平台：申请订阅消息模板（告警类），拿到模板ID
3. 小程序：加一个授权按钮调起 `wx.requestSubscribeMessage`
4. 云服务器：新增 HTTP 接口接收OneNet转发 + 调微信订阅消息API（需设备ID→openid映射）
5. 手表：新增OneNet MQTT client组件 + danger_detection注入publish调用
