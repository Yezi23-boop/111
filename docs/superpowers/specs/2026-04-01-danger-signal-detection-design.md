# 危险信号识别功能设计

## 背景

当前仓库已经具备以下基础：

- `components/audio_codec`：提供麦克风采集与 `audio_codec_init/read/deinit` 能力。
- `main/ui/generated`：主页功能入口与页面切换已由 GUI Guider 生成。
- `C:\Users\ye\Desktop\idf-EDGE_lmpulse\components\traffic_inference`：已有可在 `ESP32-S3` 上运行的危险音频识别实现，覆盖实时音频采集、重采样、滑窗推理与告警后处理。

目标是在当前项目中把“危险信号识别”做成一个独立功能：

- 用户从主页点进危险信号识别页后，后台自动开始持续监听麦克风。
- 停留在页面期间持续识别喇叭、警笛等危险信号。
- 识别到危险信号时打日志，并更新页面提示。
- 用户返回主页后立即停止识别，并释放麦克风与相关推理资源。

本次范围优先满足“最小可运行改动 + 可验证 + 可回退”，不在第一轮引入复杂的多音频业务仲裁。

## 用户流程

### 入口选择

- 复用主页当前未绑定功能的 `screen_main_option_6` 入口。
- 该入口当前图标为麦克风，语义和危险信号识别功能匹配。
- 不复用 `option_5`，避免与当前时间页功能冲突。

### 页面行为

1. 用户在主页点击 `option_6`。
2. UI 进入新的危险信号识别页面。
3. 页面加载完成后自动启动后台识别服务。
4. 页面停留期间持续显示识别状态。
5. 用户点击返回主页。
6. UI 先请求停止后台识别服务。
7. 服务停止并释放资源后，页面切回主页。

## 架构设计

### 模块划分

#### 1. `components/traffic_inference`

从外部工程迁入独立组件，保留其模型与推理能力，职责包括：

- Edge Impulse 模型与依赖编译集成
- 音频重采样
- 滑动窗口推理
- 推理结果后处理
- 危险信号告警判定

该组件不直接操作 LVGL，不直接持有页面对象。

#### 2. `main/danger_detection_service.[ch]`

新增一个薄应用层服务，负责运行时生命周期管理：

- 启动后台识别任务
- 停止后台识别任务
- 管理麦克风与推理组件初始化/释放顺序
- 缓存最近识别状态
- 向 UI 暴露只读状态查询接口

该服务是 UI 与推理组件之间的唯一桥接层。

#### 3. UI 层

主要改动在：

- `main/ui/generated/events_init.c`
- 可能新增少量 `main/ui/custom` 辅助逻辑
- 新增危险信号识别页面对应的 GUI 生成代码或手写页面装配逻辑

UI 仅负责：

- 进入页面时调用 `danger_detection_service_start()`
- 离开页面时调用 `danger_detection_service_stop()`
- 周期性读取服务状态并更新页面文本/样式

UI 不直接读取麦克风，不直接调用推理底层接口。

## 生命周期与线程模型

### 后台识别任务

危险信号识别在独立 FreeRTOS 任务中执行，不在 LVGL 线程中做推理。

推荐状态机：

- `IDLE`
- `STARTING`
- `RUNNING`
- `STOPPING`
- `ERROR`

### 启动顺序

1. UI 请求 `danger_detection_service_start()`
2. 服务检查当前状态，避免重复启动
3. 服务创建后台识别任务
4. 识别任务初始化推理状态
5. 调用 `audio_codec_init()`
6. 注册后处理告警回调
7. 进入实时识别循环
8. 状态切换为 `RUNNING`

### 停止顺序

1. UI 请求 `danger_detection_service_stop()`
2. 服务设置停止标志并切换为 `STOPPING`
3. 识别循环检测到停止请求后退出
4. 注销告警回调
5. 调用 `audio_codec_deinit()`
6. 释放滑窗状态、推理状态与任务句柄
7. 状态切换为 `IDLE`

### 线程安全策略

- 后台任务绝不直接操作 LVGL 对象。
- 服务内部维护一份共享状态结构，供 UI 轮询读取。
- 共享状态只保存轻量字段，例如：
  - 服务状态
  - 最近稳定标签
  - 最近事件时间戳
  - 最近错误码
- UI 侧通过定时器或页面内刷新逻辑读取状态并更新页面。

这样可以避免跨线程直接调用 LVGL 导致的线程安全问题。

## 识别结果与页面表现

### 识别标签

第一轮只显式支持以下稳定标签：

- `none`
- `horn`
- `siren`

中文显示建议：

- `none` -> `正在监听`
- `horn` -> `检测到喇叭`
- `siren` -> `检测到警笛`

### 页面状态

页面至少展示：

- 当前运行状态：`初始化中 / 正在监听 / 检测到喇叭 / 检测到警笛 / 停止中 / 启动失败`
- 最近一次告警时间或简单提示文本
- 返回主页按钮

第一轮不要求复杂动画，只要求状态可观测、切换可靠。

## 音频与资源约束

### 麦克风占用策略

- 危险信号识别页面运行期间独占麦克风输入。
- 离开页面时必须释放 `audio_codec`，避免长期占用输入资源。
- 第一轮不与 `official_chat` 做复杂的动态抢占协商。

适用边界：

- 该设计默认用户不会在危险信号识别页内同时启动其他需要麦克风输入的功能。
- 若后续确需并发音频输入能力，需要单独设计音频输入仲裁层。

### 内存与性能

移植 `traffic_inference` 后需要重点关注：

- Flash 占用增加
- 推理状态与模型缓冲对 RAM/PSRAM 的占用
- 后台任务栈大小
- 实时推理耗时是否影响 UI 流畅度

第一轮以可运行为主，优化属于后续迭代。

## 错误处理

### 启动失败

若 `audio_codec_init()`、任务创建或推理状态初始化失败：

- 服务状态置为 `ERROR`
- 打印明确日志
- 页面显示 `启动失败`
- 不保留半初始化资源

### 运行中故障

若识别循环中的 `audio_codec_read()` 或推理处理失败：

- 记录错误码和日志
- 结束识别循环
- 执行完整清理
- 服务状态置为 `ERROR`

### 停止超时

若停止流程超时：

- 明确打日志
- 保留错误状态供 UI 展示
- 避免静默失败导致残留任务或未释放麦克风

## 风险与回滚

### 主要风险

- 模型移植后编译时间、Flash、RAM 占用明显上升
- 麦克风资源释放不彻底导致二次进入失败
- 识别任务和 UI 刷新之间的线程边界处理不当
- 误把已有生成页面或事件逻辑改坏

### 回滚策略

- 保持危险信号功能的改动集中在新增组件、独立服务和 `option_6` 事件绑定
- 若功能不稳定，可先移除 `option_6` 事件绑定并不影响主页其他功能
- 若模型集成引入构建问题，可临时去掉 `traffic_inference` 组件依赖，恢复到无危险信号功能状态
