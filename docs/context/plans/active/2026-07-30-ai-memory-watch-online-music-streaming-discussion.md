# AI Memory Watch 在线音乐播放讨论稿

## 讨论目标

让 ESP32-S3 手表通过自身扬声器稳定在线播放用户有权播放的音乐；先形成可验证的小闭环，再决定是否进入实施计划。

这不是桌面播放器遥控功能，也不改变 AI Memory Watch 作为 Hermes 随身输入与交互终端的定位。

## 已确认边界

- 音频数据不经过 Hermes、Gateway Relay 或现有对话 WSS。
- 网易云账号授权只在服务器侧完成；ESP32 不保存账号、密码、Cookie 或平台播放链接。
- `api-enhanced` 仅作为服务器私有的试验性上游，禁止向公网或 ESP32 暴露其通用接口。
- 不启用任何解锁、绕过版权或规避平台限制的能力；只处理用户账号正常可播放的内容。
- 现有 `audio_codec` 继续拥有扬声器 output session；录音/Hermes 前台输入与音乐播放必须明确仲裁，不能同时抢占麦克风和扬声器资源。
- 手表只承担 HTTPS 拉流、PSRAM 缓冲、解码、播放和轻量 UI；音乐目录、登录、播放 URL 更新、转码与断流恢复归服务器所有。

## 候选架构

```text
手表 UI / Hermes 音乐意图
  -> music gateway（公网窄接口，device token）
  -> 私有 Netease API（Docker 内网，账号 Cookie）
  -> 上游正常播放资源
  -> music gateway 代理或转码为固定音频流
  -> 手表 HTTPS 拉流 -> PSRAM 环形缓冲 -> 解码 -> ES8311 扬声器
```

`music-service` 是新增的独立服务，不混入 `watch_voice_endpoint` 的 ASR、Hermes session 或收件箱职责。单用户首版将网易云适配、二维码授权、播放会话、队列逻辑与实时转码收在这一个容器中，而不再额外部署 `ncm-api` 容器。它对手表只暴露曲目目录、播放控制和已鉴权的音频流。

播放会话实时读取上游资源、转码为固定 `MP3 / 24 kHz / mono / 64 kbps` 并持续下发给手表；不下载或持久化整首歌曲。

## 推荐最小闭环

1. 服务器生成一个固定、短期有效的 HTTPS MP3 流。
2. 手表用现有音频输出链路连续播放 30 分钟，无卡死、无 stack overflow、无持续性缓冲中断。
3. 服务器再接入个人账号的“我喜欢”列表，手表分页选择一首歌并开始播放。
4. 最后才接入 Hermes 的“播放我的收藏”意图和搜索候选。

第一版音频 profile 固定为 `MP3 / 24 kHz / mono / 64 kbps`，以匹配当前板端固定 24 kHz 输出并减少 Wi-Fi、PSRAM 与解码压力。网易云上游实际格式、码率与设备条件并不固定，必须由服务器统一归一化后再下发给手表。

## 首版交互候选

```text
音乐页
  今日推荐
  我的喜欢
  我的歌单
  最近播放
  搜索

播放页
  封面或占位图
  歌名 / 歌手
  播放 / 暂停
  上一首 / 下一首
  音量
  缓冲中 / 播放中 / 网络恢复中
```

精确拖动进度、逐行歌词、无损音频、缓存整首歌曲、离线下载和多设备同步不属于首版范围。

音乐播放开始后，离开音乐页面仍保持后台播放。系统上拉栏增加一个播放控制按钮：短按切换播放/暂停；长按停止播放并销毁本次音乐运行服务，释放音频 output session、HTTPS 流、PSRAM 缓冲与播放任务。长按不清除服务器账号授权、曲库元数据或最近播放记录。

## 已决策：独立音乐页面

音乐作为独立功能入口，进入后展示音乐目录或播放页；不嵌入 Hermes 页面，不复用 Hermes 对话记录或对话 UI。首版不支持 Hermes 语音意图控制音乐；Hermes 不承担音频传输、播放控制或播放器页面状态。

## 登录授权草案

服务器创建短生命周期 QR 登录会话，手表只显示二维码位图与 `等待扫码/等待确认/已登录/已过期` 状态。服务器轮询上游登录状态；授权成功后将 Cookie 写入受限私有 secret 存储。二维码会话、二维码内容和 Cookie 都不得进入日志、仓库或 ESP32 NVS。

## 已决策：首版选歌范围

首版只做“今日推荐 + 我喜欢 + 我的歌单 + 最近播放”。搜索、语音点歌、结果分页和重名消歧留到后续阶段。

“今日推荐”由 music-service 在服务器侧调用已登录网易云账号的每日推荐歌曲能力取得；手表仍按每页 10 首分页显示。它不是 Hermes 推荐，也不把网易云通用推荐接口暴露给 ESP32。

## 待讨论：第 2 题

播放模式应由哪一端执行？

已决定：手表只切换并上报 `repeat_one`、`repeat_all` 或 `shuffle` 模式，以及上一首/下一首意图；不维护播放队列、随机历史或歌曲排序。

`music gateway` 以网易云返回的当前来源歌单为依据，持有本次播放会话，决定下一首、上一首、循环和随机规则，再创建新的短期音频流。网易云 API 是私有上游目录和播放资源提供方，并不作为手表的长期播放状态 owner。

## 已决策：暂停释放音频管线

短按暂停时，手表停止读取音频，服务器立即停止当前 FFmpeg 转码与上游流连接；两端只保留本次会话的曲目、完整来源队列、播放模式与近似播放进度。继续播放时新建短期音频流，不需要 pause heartbeat，也不占用后台转码资源。

## 待讨论：第 5 题

音频流传输协议应选择 HTTPS 分块流、WSS、HLS 还是 UDP/RTP？

已决定：音频使用 `HTTPS / TCP` 持续分块 `audio/mpeg` 流。手表以 `esp_http_client_open()` 后连续 `read()` 的方式读取 MP3 字节，写入 128 KB PSRAM 环形缓冲并逐步解码；服务器边转码边输出，不下载或缓存整首歌。

不使用 WSS、HLS、UDP/RTP 或 MQTT 传输首版音频。WSS 继续只服务于现有 Hermes 前台对话；音乐控制保持独立 HTTP JSON。

## 待讨论：第 6 题

首版播放页是否显示歌曲进度时间（例如 `01:12 / 03:45`）？

- **推荐：不显示精确时间，只显示“缓冲中/播放中/暂停/网络恢复中”等状态。** 首版不提供 seek，且暂停恢复采用近似进度，避免把估算时间误导成精确播放位置。
- 可选：显示近似时间。信息更多，但需持续本地计时并处理重连、缓冲和 seek 回退的校准偏差。

当前推荐选择：首版不显示精确进度时间。

“我喜欢”和“我的歌单”继续遵循服务器缓存上游目录 5 分钟、首次或过期时刷新的策略。

## 后续讨论顺序

1. 首版选歌范围。
2. 离开音乐页面后的播放生命周期。
3. 音频格式、PSRAM 缓冲目标与断流恢复语义。
4. music gateway 的最小接口、鉴权和短期播放会话。
5. 二维码登录的页面、失效和换号策略。
6. 选歌 UI、后台播放与功耗边界。
7. 通过讨论后拆分为可执行 server/ESP32 计划。
