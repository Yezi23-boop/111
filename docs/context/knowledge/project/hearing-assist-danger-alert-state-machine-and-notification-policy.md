# 听障危险提醒状态机与提醒策略草案

## 目标

- 本文是 [hearing-assist-danger-alert-system-architecture.md](D:\esp32S3\111\docs\context\knowledge\project\hearing-assist-danger-alert-system-architecture.md) 的下钻文档。
- 目标是把“危险提醒系统”进一步落成可执行的状态机与提醒策略，而不是继续停留在抽象架构层。
- 本文重点解决的问题是：
  - 模型输出如何进入用户可感知的提醒状态
  - 如何降低误报造成的打扰
  - 如何避免告警抖动、重复震动和频繁闪屏
- 若要确认这些状态和策略在当前固件中的真实落点与缺口，应继续查看：
  - [hearing-assist-danger-alert-firmware-mapping.md](D:\esp32S3\111\docs\context\knowledge\project\hearing-assist-danger-alert-firmware-mapping.md)

## 设计原则

- 用户收到的是“稳定提醒”，不是单窗分类结果。
- 单个高风险窗口不能直接触发正式危险提醒。
- 正式危险提醒必须有确认条件、保持策略和清除条件。
- 用户体验优先级默认遵循：
  - `可靠`
  - `及时`
  - `低打扰`
  - `可解释`

## 输入与输出边界

### 上游输入

- 风险融合层输入至少包括：
  - `danger_prob`
  - 当前窗口时间戳
  - 可选事件来源倾向，例如 `horn / siren / alarm`
- 该层不依赖某一种固定特征，也不依赖某一个固定模型。

### 下游输出

- 状态机层输出不应只是一位布尔值。
- 建议下游输出至少包括：
  - 当前提醒状态
  - 当前提醒级别
  - 最近一次危险确认时间
  - 最近一次危险来源提示

## 推荐状态定义

### `Off`

- 功能关闭或当前不可用。
- 不采集、不推理、不提醒。
- 用于用户手动关闭、系统未初始化完成、或资源被其他高优先级模块占用时。

### `Monitoring`

- 功能已启用，正在持续监听。
- 当前未检测到足够强的风险证据。
- 这是正常稳态，也是绝大多数时间应处于的状态。

### `Suspicious`

- 已出现一到多个高风险窗口，但尚未达到正式危险确认条件。
- 该状态的意义是承接“模型已经觉得不对劲，但系统还不想惊动用户”的中间层。
- 设计这层的原因是减少偶发尖峰、短促误判和单窗异常导致的误报。

### `Alerting`

- 已满足正式危险确认条件。
- 系统应进入强提醒状态，并保证在短时窗口内不要来回抖动。
- 该状态是用户真正需要感知并采取注意动作的状态。

### `Cooldown`

- 危险刚刚解除，系统进入短暂抑制期。
- 在这个阶段，系统不应立刻因为零星尖峰再次进入完整强提醒流程。
- 其目标是防止告警边缘来回翻转，避免连续多次强震动。

## 推荐状态转移

### `Off -> Monitoring`

- 条件：
  - 用户主动开启
  - 所需音频资源就绪
  - 推理运行时初始化完成

### `Monitoring -> Suspicious`

- 条件：
  - 当前窗口 `danger_prob` 达到可疑阈值
  - 但尚未满足正式告警确认条件
- 目的：
  - 吸收单窗高风险尖峰
  - 为后续连续确认提供缓冲

### `Suspicious -> Alerting`

- 条件：
  - 连续观察窗口中满足正式危险确认条件
  - 推荐口径：`最近 3 个窗口中至少 2 个达到高阈值`
- 该条件属于当前最推荐的首版策略，因为它在“及时”和“低误报”之间较平衡。

### `Suspicious -> Monitoring`

- 条件：
  - 可疑证据未持续
  - 连续窗口快速回落到安全区

### `Alerting -> Cooldown`

- 条件：
  - 已经过了最短提醒保持时间
  - 且连续多个窗口回落到非危险状态

### `Cooldown -> Monitoring`

- 条件：
  - 冷却计时结束
  - 且没有再次出现持续性高风险证据

### `Cooldown -> Alerting`

- 条件：
  - 冷却期间再次出现连续确认级危险证据
- 说明：
  - 允许重新进入告警，但应避免完全重复播放整套重型提醒节奏

## 推荐阈值与窗口策略

- 本文不把具体阈值写死成永久值，但建议长期保留三层概念：
  - `可疑阈值`
  - `确认阈值`
  - `清除阈值`
- 推荐思路：
  - `可疑阈值` 略低于正式阈值
  - `确认阈值` 偏高，优先压误报
  - `清除阈值` 低于确认阈值，形成回滞，避免抖动

### 当前建议口径

- 对首版听障提醒产品，推荐继续采用高阈值路线。
- 当前主线可维持类似如下设计思想：
  - `2/3` 连续窗口确认进入 `Alerting`
  - 进入后设置最短 hold
  - 连续多个安全窗口后才允许退出
  - 退出后进入 `Cooldown`

### 为什么不用“单窗即报警”

- 因为环境中存在大量瞬时尖峰：
  - 人声爆破音
  - 摩擦
  - 外放音频瞬态
  - 佩戴碰撞
- 单窗即报警会显著降低用户对功能的信任。

## 提醒分级建议

### `Suspicious` 提醒

- 默认建议：
  - 不触发强震动
  - 不强占屏幕
  - 最多允许极轻量、可关闭的弱提示
- 第一版甚至可以完全不对用户暴露 `Suspicious`，只作为内部状态保留。

### `Alerting` 提醒

- 这是核心危险提醒态。
- 建议动作：
  - 立即触发强震动
  - 屏幕进入明确危险提示态
  - 如果当前 UI 已在危险识别页，可直接进入高对比度警示显示
- 2026-05-13 当前产品决策：AI 对话页前台期间暂停 Safety Monitor，退出 AI 对话后如果安全监听开关仍开启再自动恢复；因此不在提醒层额外判断 `official_chat` 的 `SPEAKING` 状态。

### `Cooldown` 提醒

- 不应再继续强震动。
- 可保留轻量状态反馈，例如：
  - 屏幕仍显示“刚刚检测到危险”
  - 或在后台保留事件记录

## 震动策略建议

### 设计原则

- 震动是第一优先提醒通道。
- 对听障用户，震动往往比屏幕更及时。
- 震动不能频繁、零碎、无节奏，否则会快速造成烦躁和麻木。

### 推荐策略

- `Suspicious`：
  - 默认不震动，或仅在“敏感模式”下使用极轻提示
- `Alerting` 首次进入：
  - 触发一次明显、可区分于普通通知的强震动模式
- `Alerting` 持续期间：
  - 不要每个推理窗都重复震动
  - 允许按固定周期补一次较轻提醒，前提是危险持续存在
- `Cooldown`：
  - 不再强震

### 与普通通知的区分

- 危险提醒震动节奏应和消息通知、来电、系统提示有明显差异。
- 目标是让用户建立“这不是普通提醒，而是环境风险”的肌肉记忆。

## 屏幕策略建议

### 设计原则

- 屏幕是辅助通道，不应成为唯一提醒手段。
- 屏幕内容应简单直接，减少解释负担。

### 推荐显示策略

- `Monitoring`：
  - 正常待机或普通识别页状态
- `Suspicious`：
  - 第一版可以不显示特殊状态
- `Alerting`：
  - 使用高对比度危险态
  - 文案应简短，例如“检测到危险声音”
  - 如需显示来源，建议作为次要信息
- `Cooldown`：
  - 可在短时间内保留“危险已解除”或回到正常页

### 不建议的做法

- 不建议在首版里堆太多类别细节。
- 不建议在告警态显示长文本说明。
- 不建议把屏幕设计成依赖用户持续阅读才能理解。

## 用户策略档位建议

### `保守模式`

- 更高确认门槛
- 更长清除条件
- 更少误报
- 更适合对误报极敏感的用户

### `标准模式`

- 当前默认模式
- 平衡召回与误报

### `敏感模式`

- 更容易进入 `Suspicious` 或 `Alerting`
- 适合对漏报更敏感、可接受更多打扰的用户

## 事件记录建议

- 即使首版不做复杂回放，也建议至少记录：
  - 事件时间
  - 事件状态级别
  - 持续时长
  - 可选来源提示
- 其用途包括：
  - 用户事后理解刚才发生了什么
  - 工程侧复盘误报与漏报
  - 后续训练数据回收

## 与当前实现的关系

- 当前仓库已具备基础危险识别链路与提醒链路，但本文档比当前实现抽象层更高。
- 当前实现中的阈值、连续窗口数、hold 和 clear 参数，属于这一状态机草案的“当前实例”，不是永久不可变规则。
- 后续如果更换模型、特征或训练数据，本草案仍应作为产品行为层的稳定约束。

## 当前推荐落地顺序

### 第一阶段

- 固定 `Monitoring / Alerting / Cooldown` 主流程
- `Suspicious` 先作为内部状态，不强暴露给用户
- 强提醒只在 `Alerting` 首次确认时触发

### 第二阶段

- 加入灵敏度档位
- 优化强震动与补提醒节奏
- 优化清除和冷却体验

### 第三阶段

- 再考虑是否把 `Suspicious` 以轻量方式暴露给用户
- 再考虑来源提示和事件回放能力

## 对后续实现的约束

- 不允许把单窗高风险直接等同于用户级危险提醒。
- 不允许让每个推理窗都重复触发强震动。
- 不允许把模型类别细节置于“可靠提醒”目标之上。
- 状态机、提醒策略与模型结构必须解耦，避免每换一版 student 模型就推倒产品行为层。
- 具体参数落地、默认值分类和用户可配置边界，应以下游文档 `hearing-assist-danger-alert-parameter-defaults-table.md` 为准。
