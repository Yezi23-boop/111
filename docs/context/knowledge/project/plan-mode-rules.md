# 计划模式规则

## 适用边界

- 本规则只在上层环境已经进入计划模式时生效。
- 本规则约束的是计划内容深度、验证闭环和风险控制，不负责决定是否进入计划模式。
- 若与更高优先级的 system / developer 指令冲突，以更高优先级规则为准。

## 必须先深度计划的任务特征

命中以下任一特征时，在计划模式下必须先给出详细计划，禁止直接编码：

- 任务涉及多个文件、模块、线程、状态机或外设。
- 任务影响接口、架构、依赖、配置、内存布局或时序。
- 需要排查 bug、定位根因或处理不确定问题。
- 需求存在歧义、缺失约束或验收标准不明确。
- 改动可能影响稳定性、实时性、安全性、功耗或资源占用。

## 最低结构

计划必须至少覆盖以下七个部分，缺一不可。

### 1. 问题重述

- 用自己的话准确重述目标。
- 明确输入、输出、边界和非目标。
- 明确当前已知信息与未知信息。

### 2. 约束清单

- 列出功能约束、性能约束、资源约束、平台约束和兼容性约束。
- 对嵌入式任务，必须显式分析：
  - RAM / Flash
  - CPU 占用
  - 实时性
  - 中断安全
  - 线程安全
  - 外设时序
  - 错误恢复
  - 功耗影响

### 3. 根因或关键难点分析

- 若是修 bug，必须先给出可能根因列表，并说明各自证据。
- 若是新功能，必须指出实现难点、隐含耦合点和失败风险。
- 不允许跳过分析直接给实现步骤。

### 4. 方案比较

- 至少给出 2 个可行方案；简单任务也必须说明为什么不需要第二方案。
- 对每个方案说明：
  - 核心思路
  - 优点
  - 缺点
  - 风险
  - 对现有代码的侵入性
  - 资源与维护成本
- 必须说明最终选择该方案的理由。

### 5. 分步执行计划

每一步都必须写清：

- 目标
- 要修改的文件 / 模块 / 接口
- 具体改动点
- 前置条件
- 可能副作用
- 完成标准

禁止使用“修改代码”“优化逻辑”“增加处理”这类空泛表述。

### 6. 验证计划

每一步都必须绑定验证方法，不能只写“运行测试”：

- 单元测试
- 集成测试
- 日志观察点
- 边界条件测试
- 异常路径测试
- 性能 / 内存 / 时序验证
- 回归测试范围

### 7. 风险与回滚

- 列出最可能出错的点。
- 给出失败信号。
- 给出回滚或降级策略。
- 指出哪些结论依赖假设，假设不成立时如何调整计划。

## 粒度要求

- 计划必须细到“可直接执行”，而不是只描述阶段名称。
- 合格示例：在 `components/lvgl_port/lv_port.c` 中为显示刷新增加等待点统计和超时保护，并在 `components/co5300_panel/co5300_panel.c` 中补 TE 中断观测与失败回退路径。
- 不合格示例：优化显示刷新逻辑。

## 思考深度自检

输出计划前必须自检以下问题；若任一答案是否，继续完善计划，不得进入编码：

- 我是否真正理解了目标和非目标？
- 我是否识别了最关键的约束？
- 我是否分析了失败模式而不是只分析成功路径？
- 我是否比较了备选方案？
- 我是否说明了为什么选这个方案？
- 我是否给出了可执行、可验证、可回滚的步骤？
- 我是否遗漏了资源、时序、并发、错误恢复方面的问题？

## ESP32 / MCU 额外要求

对于 ESP32 / MCU 项目，计划必须额外分析：

- 任务运行在哪个上下文：中断、任务、回调或主循环。
- 是否存在竞态、死锁、优先级反转或阻塞过久。
- 是否会导致栈溢出、堆碎片或内存泄漏。
- 是否影响 DMA、I2S、SPI、UART、ADC、Wi-Fi、BLE 等外设行为。
- 是否影响 watchdog、功耗、启动时序或异常恢复。
- 是否需要考虑 ESP-IDF、芯片型号、驱动 API 差异等版本兼容问题。

## 编码前置要求

在计划获得批准前：

- 不得直接改代码。
- 不得跳过方案比较。
- 不得省略验证与风险分析。
- 不得用“先实现再说”的方式替代设计。

## 输出风格要求

- 计划必须具体、可执行、可审查。
- 避免空话、套话和管理化表达。
- 少写“提高性能、增强稳定性”这类泛化结论。
- 多写“改哪里、为什么、怎么验、失败怎么办”。

## 计划质量否决规则

出现以下任一情况，视为计划不合格，必须重做：

- 只有步骤，没有原因。
- 只有方案，没有约束。
- 只有成功路径，没有失败路径。
- 只有实现思路，没有验证方法。
- 只有“改动模块”，没有具体文件 / 接口 / 状态。
- 没有备选方案，或没有说明为什么不需要备选方案。
- 没有说明风险、假设和回滚策略。
- 使用“优化、增强、完善、处理”这类空泛词但没有展开。

禁止输出类似以下浅层计划：

1. 阅读代码
2. 修改代码
3. 测试功能
4. 提交结果

必须把每一步展开到工程可执行层。
