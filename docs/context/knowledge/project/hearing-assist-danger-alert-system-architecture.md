# 听障危险提醒系统架构草案

## 产品目标

- 本功能的目标不是做泛音频分类，而是把环境中的高价值危险声学信号，转换成听障用户可以及时感知、愿意长期开启、且足够可信的手表提醒。
- 第一目标是公共场所与交通环境下的风险提醒，例如过马路、车辆从背后接近、警笛接近、公共报警器持续响起。
- 最终交付给用户的是“可靠提醒”，不是模型类别名本身。

## 核心用户与使用场景

- 核心用户：听力障碍用户，尤其是对环境危险提示有补偿需求的人群。
- 典型场景：
  - 过马路时背后车辆鸣笛
  - 路口、商场、地铁等嘈杂公共环境中的警笛或报警声
  - 日常行走中用户未注意到的持续危险提示音
- 产品价值重点是“帮用户尽快注意到风险”，而不是“告诉用户环境里所有声音都是什么”。

## 主线 danger 定义

- active 主线 danger 只包含以下核心危险声学信号：
  - `siren`
  - `horn / car_horn`
  - `alarm / smoke_alarm / fire_alarm / clock_alarm`
- 主线输出建议统一收敛为 `danger / non_danger`，而不是把首版产品做成多类展示型分类器。
- 如果内部模型保留 `horn / siren / alarm` 候选来源，也应优先作为调试或后续分析信号，而不是当前产品主承诺。

## 当前明确非目标

- 不做语义理解，不根据“人说了什么”来触发危险提醒。
- 不承诺识别所有突发异响。
- 不承诺判断危险距离、方向和真实物理位置。
- 不承诺区分“环境真实危险声”和“外放设备播放的危险声”。
- 当前不把“救命 / 着火了 / 报警”等中文语义喊叫直接纳入 active 主线 danger。

## 系统分层

### 1. 感知输入层

- 负责采集环境声音，以及未来可能引入的辅助上下文。
- 当前核心输入是麦克风音频。
- 长期可扩展输入包括：
  - 用户运动状态
  - 时间段
  - 场景模式
  - 未来外设或手机侧上下文
- 这一层只负责收集输入，不直接做危险判定。

### 2. 信号表达层

- 负责把原始音频窗口转换成模型可消费的中间表示。
- 该层不应在产品架构里写死为某一种特征。
- 允许替换的实现包括：
  - `Fbank`
  - `Log-Mel`
  - `MFCC`
  - 轻量 learnable front-end
- 长期固定约束只有三条：
  - 输入输出接口稳定
  - 窗口输入 shape 固定
  - 训练、导出、设备侧实现严格一致

### 3. 事件识别层

- 负责从单个时间窗口中提取“像不像危险事件”的概率性结论。
- 该层输出应保持中性，建议包括：
  - `danger_prob`
  - 候选事件来源倾向
  - 置信度或不确定度
- 该层不应直接驱动 UI，也不应直接承担误报控制的全部责任。

### 4. 风险融合层

- 这是产品体验的核心层，负责把抖动的单窗结果变成稳定可信的风险结论。
- 该层负责融合：
  - 连续窗口输出
  - 事件优先级
  - 用户配置
  - 场景策略
  - 抖动抑制与清除条件
- 建议长期保留以下能力接口：
  - 进入危险确认条件
  - 告警 hold
  - 清除条件
  - cooldown 去重
  - 可疑态与确认态区分

### 5. 用户提醒层

- 负责把系统风险判断转成听障用户可快速理解的反馈。
- 提醒通道建议按优先级设计：
  - `震动`
  - `屏幕`
  - 后续可能的手机联动
- 提醒层不应只有一个强度，建议至少分为：
  - `Suspicious`
  - `Alerting`
  - `Cleared`
- 该层设计目标是高可感知、低打扰、低歧义。

### 6. 用户策略层

- 负责因人、因场景调整系统行为。
- 长期建议支持：
  - `保守 / 标准 / 敏感` 灵敏度档位
  - `仅震动 / 震动+屏幕` 提醒模式
  - 场景化策略，例如户外交通、室内公共环境、夜间安静模式
- 该层使系统从“工程 demo”走向“可长期使用的产品功能”。

### 7. 数据闭环层

- 负责沉淀事件记录、误报线索和后续训练改进依据。
- 长期建议记录：
  - 最近危险提醒事件
  - 提醒类型和持续时间
  - 用户是否快速手动关闭
  - 容易误触发的典型场景
- 即使首版不做云端学习，也应在架构上预留本地记录与复盘入口。

## 功能状态机建议

- 建议系统状态至少包含：
  - `Off`
  - `Monitoring`
  - `Suspicious`
  - `Alerting`
  - `Cooldown`
- 这样可以避免把系统粗糙地压缩成“有危险 / 没危险”两态，便于后续做防抖、提醒强度分级和用户策略切换。

## 产品优先级

- 第一优先：低误报，避免用户因为普通声音频繁被打扰而关闭功能。
- 第二优先：核心 danger 召回，尤其是 `horn / siren / alarm`。
- 第三优先：板端实时性、RAM/Flash 占用与稳定性。
- 第四优先：更细粒度的类别解释与展示。

## 数据边界与训练口径

- active 主线训练只围绕 `siren / horn / alarm` 展开。
- 大声中文人声、普通喊话、电视/短视频/直播人声、商场/地铁环境声、手表佩戴摩擦声，应优先作为 `non_danger hard negative`。
- 如果人声背景里同时存在真实 `siren / horn / alarm`，不能简单因为有人声就标为 `non_danger`，应按 danger 或混合正样本处理。
- `glass_break / crash / impact` 当前只保留在 extended challenger 路线，不进入默认 active 口径。

## 演进路线

### 第一阶段：核心公共安全提醒

- 目标：稳定提醒 `horn / siren / alarm`
- 输出：`danger / non_danger`
- 特点：高阈值、强防抖、震动优先

### 第二阶段：抗干扰增强

- 重点补齐：
  - 中文大声人声
  - 电视/短视频外放
  - 手表摩擦、衣物摩擦、敲击佩戴噪声
  - 公交、地铁、商场等公共环境负样本

### 第三阶段：扩展事件实验

- 只在不破坏 active 主线的前提下，试验：
  - `glass_break`
  - `impact`
  - `crash`
  - 其他突发异响

### 第四阶段：场景化与个性化

- 加入：
  - 模式切换
  - 灵敏度档位
  - 事件记录
  - 手机联动或更多反馈方式

## 与当前实现的关系

- 当前 active 模型、特征实现、阈值和防抖参数属于“当前实现层”，不是本架构草案的永久约束。
- 后续允许替换：
  - 特征类型
  - student 模型结构
  - 推理后处理细节
- 但应保持以下长期不变边界：
  - 产品目标面向听障用户的危险提醒
  - active 主线 danger 聚焦 `siren / horn / alarm`
  - 用户拿到的是稳定提醒，而不是生硬分类输出

## 对后续实现的约束

- 任何新模型、新特征或新训练策略，都应回答它是否提升了“可靠提醒”而不是只提升离线测试准确率。
- 任何 extended 事件实验，都不得默认覆盖 active 主线 danger 定义。
- 任何 UI/交互改动，都应优先服务于听障用户的及时感知与低打扰体验。
- 更细的状态流转、提醒分级、震动与屏幕策略，应以下游文档 `hearing-assist-danger-alert-state-machine-and-notification-policy.md` 为准。
- 更细的参数级别、默认值建议和用户可配置边界，应以下游文档 `hearing-assist-danger-alert-parameter-defaults-table.md` 为准。
