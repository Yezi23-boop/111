# ESP32/MCU 嵌入式 C/C++ 工程规则

## 适用范围

- 本规则默认适用于本仓库中的代码生成、代码评审、重构和架构建议任务。
- 本规则服务于 `ESP32-S3 + ESP-IDF + LVGL` 固件工程，但其中的大部分工程约束也适用于一般 MCU 平台。
- 若与更高优先级的 system、developer 或仓库顶层规则冲突，以更高优先级规则为准。

## 目标优先级

- 正确性 > 安全性 > 稳定性 > 可维护性 > 资源效率 > 开发便利性

## 架构与模块边界

- 必须优先采用模块化、组件化、单一职责设计。
- 后续新增功能、跨文件改动、模块重构和架构评审，默认按 `App/UI -> Service -> Manager/Domain -> Driver Adapter -> Vendor/SDK` 判断 owner 与调用方向；详细项目边界见 `docs/context/knowledge/project/layering-boundary-map.md`。
- `App/UI` 只表达用户动作、页面状态和业务入口；不得直接拥有底层 SDK、器件、协议或后台生命周期。
- `Service` 负责后台生命周期、状态推进、重试、超时、任务协作和跨模块编排；不得反向依赖具体页面对象。
- `Manager/Domain` 负责领域语义、资源 owner 和稳定公开接口；不得退化成“什么都能塞”的大杂烩。
- `Driver Adapter` 负责 SDK、协议、寄存器、上电顺序、总线时序和错误码翻译；不得把产品策略塞进驱动适配层。
- `Vendor/SDK` 是不可控变化点，只能由对应 adapter/driver owner 直接接触；上层不得散落直接调用。
- 禁止业务逻辑直接访问硬件寄存器。
- 禁止应用层直接依赖底层驱动内部实现。
- 模块之间只能通过公开接口通信，禁止跨模块直接访问内部状态。
- 新增抽象前必须确认是否存在真实替换风险、多个调用者、测试替身需求或明显的错误处理收敛价值；禁止为了形式分层增加空 wrapper。
- 算法/AI 层必须拆分为以下最小职责单元：
  - 预处理
  - 推理
  - 后处理
  - 模型配置

## 复杂度控制

- 应优先控制文件规模；单文件若明显超过 1000 行，应先检查是否可以按职责拆分。
- 应优先控制函数复杂度；圈复杂度通常建议不超过 10。
- 条件与循环嵌套通常不应超过 3 层；若更深，应优先通过提前返回、辅助函数、状态拆分或查表方式重构。
- 函数参数通常建议不超过 5 个；若超过，应先检查是否职责过多，或是否需要有意义的结构化封装。
- 若逻辑过长、职责混杂或阅读成本高，必须优先拆分为职责明确的辅助函数或子模块。
- 当复杂度控制与正确性、安全性冲突时，优先保证正确性与安全性。

## 风格与可读性

- 新增或修改代码默认按 Google Code Style 靠拢。
- 命名必须语义明确，禁止无意义命名。
- 禁止魔法数字，必须提取为常量、枚举或配置项。
- 注释应解释“为什么”，不能只重复代码表面含义。
- 新增或修改公开接口、跨模块接口或非显然函数时，默认补 `Doxygen` 风格中文函数头注释；实现内部普通说明注释优先使用 `//`，多行原因说明可使用 `/* ... */`。
- 关键变量、共享变量、协议常量和魔法数字必须解释用途、单位、来源或并发边界。
- 单次调用、逻辑很短、缺乏独立语义且预计不会复用的小函数，默认内联到调用处，减少阅读跳转成本。
- 不要为了形式上的“面向对象”或“解耦”引入过度抽象；避免增加仅转发一层的 wrapper、无实质封装价值的 getter/setter，或没有信息增量的接口。
- 只有在复用、独立语义、可测试性、副作用隔离、错误处理收敛或明显提升可读性时，才引入新的函数或抽象层。
- 当任务目标只是补注释或仅提升代码可读性时，默认先只改注释；若注释仍无法解决问题，必须先获得用户明确允许，才可做最小重构。
- 禁止为求简短而牺牲可读性、边界检查或错误处理。

## 内存与资源约束

- 必须优先使用静态分配或受控内存分配。
- 禁止在高频路径中频繁 `malloc/free` 或 `new/delete`。
- 所有缓冲区和数组访问都必须做边界检查。
- 禁止生成潜在栈溢出的超大局部变量。
- 必须优先考虑低 RAM、低 Flash 占用实现。
- 禁止把资源申请、硬件控制和业务流程耦合在同一个复杂函数中。

## 安全与异常处理

- 必须检查关键函数返回值。
- 所有输入必须做空指针、范围、长度和状态检查。
- 所有错误路径必须可控，不能静默失败。
- 初始化失败、数据异常、超时、推理失败时，必须返回安全默认值或进入降级路径。
- 禁止在中断上下文中执行耗时 AI 推理。
- 禁止输出未初始化数据。
- 若存在潜在风险但当前证据不足，必须显式标注假设和适用边界。

## 算法/AI 实现专项要求

- 模型输入尺寸、量化参数、阈值必须集中定义在配置层或模型配置模块。
- 禁止把模型参数、阈值和业务逻辑硬编码在同一段流程里。
- 预处理、推理和后处理必须解耦。
- 推理接口必须明确输入、输出和状态码。
- 当置信度低于阈值时，必须执行“不触发”或“安全默认动作”。
- 对 ESP32 / MCU 平台，默认优先采用轻量实现，不生成不切实际的大模型方案。

## 接口契约

- 所有公开接口必须有清晰的输入、输出和返回值定义。
- 返回值应能区分成功、失败、超时、参数错误、状态错误等结果。
- 禁止接口隐式修改外部全局状态。
- 禁止用全局变量作为模块之间的主要通信方式；若确有必要，必须封装并限制访问范围。

## 输出与自检要求

- 涉及新增模块、跨文件改动或明显重构时，输出代码前，应先给出文件划分方案和模块职责说明。
- 若用户未要求完整工程，不输出无关样板代码。
- 生成前必须自检以下项目：
  - 是否模块化，是否存在明显高耦合
  - 是否存在职责混杂的大文件或大函数
  - 是否存在可重构的深层嵌套
  - 是否使用不安全函数或缺少边界检查
  - 是否检查关键返回值
  - 是否提供异常降级路径
  - 是否符合 Google Code Style
- 若发现明显问题，应先重构方案再输出，而不是直接给出“能跑但不可维护”的代码。

## 非目标与兼容边界

- 本规则主要约束后续新增或修改代码，不要求一次性重构全部历史代码。
- 本规则不要求为了风格统一而大面积重排无关旧代码。
- 若用户请求与本规则存在张力，应优先满足正确性、安全性和仓库更高优先级规则，并在答复中说明取舍原因。
